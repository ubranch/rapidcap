Errors & feedback

Three states the product has in code and had nothing in design: CaptureState::Error, a successful save, and the panel while the overlay is open.

Error — replaces the footer

Recording failed — disk full
The whole footer becomes the error. Chips are gone — nothing else matters until this is read.
Screen capture unavailable — another app is using the display
Not everything can be retried. Retry appears only when the failed command is idempotent.
Encoding failed — see details
Long technical strings are summarised; the raw error lives in the tooltip and behind Copy log.
Amber, not red. Red already means "capture is running" in this product — a red error bar under a red recording frame is unreadable. --warn #E8A33D is the only new colour in the system, and it exists solely so failure never gets confused with recording.
Code delta: controller.rs:124 silently drops the error on the next command (if matches!(self.state, CaptureState::Error(_)) { self.state = CaptureState::Idle; }), so today the message vanishes when the user clicks anything. This spec needs the error to survive until dismissed or until the next capture succeeds, and Error(String) to carry a short summary plus the raw detail rather than one blob.

A recording saved. Duration and file size land in the status well — the two things you check before sending a clip.
The confirmation is a control, not a toast. A toast that floats over the desktop is one more thing to dismiss; a chip in the footer is already where the user's eye is, is clickable, and expires on its own. Saving is the moment the product earns trust — today SavedCapture succeeds and nothing on screen changes at all.

While the overlay is open the panel steps back: every card drops to 45% except the armed one, chips hide, and the status well carries the escape route. On a single monitor the user never sees this — on two, it is the difference between a frozen app and an obvious one.
